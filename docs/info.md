## How it works

This project is an entry in Jane Street's protocol emulator ASIC competition: a small, reprogrammable
CPU that bit-bangs serial protocols from firmware instead of using a fixed-function block per protocol.

The core (`src/cpu.v`) is a **deterministic four-thread barrel processor**: four hardware threads share one
program memory and the pins, and take turns in a fixed order, one instruction each every fourth clock (a *slot*).
Every instruction takes one slot, except `WAIT n`, which takes `1 + n`. A thread's timing therefore depends only
on its own program, never on what the other threads are doing: protocol timing is a matter of counting slots,
and two protocols can run side by side without disturbing each other. There are no interrupts and no
arbitration. Threads synchronise through a one-byte blocking channel (`SEND` / `RECV`) and start each other
with `SPAWN`. The instruction set and the architecture are in `docs/isa.md`.

The firmware lives in `src/rom.v`, generated by `tools/build_rom.sh` from `firmware/*.asm`. At boot a
small dispatcher on thread 0 reads the mode pins and jumps to one of four programs:

- **No mode pin: UART transmitter**, 8N1 at 432 clocks per bit (50 MHz / 115200 baud, 0.5 % fast).
- **`uio[7]` high: SPI master**, mode 0, MSB first, 16-bit frames. It sends `ui[7:0]`, receives a byte
  from the slave, and sends the received byte straight back as a built-in self-test.
- **`uio[6]` high: I2C master** (standard mode, about 100 kHz, with clock stretching). It does an EEPROM-style
  random read: write the pointer byte from `ui[7:0]` to the device at address 0x50, repeated START,
  read one byte, STOP, and then **prints that byte on the UART**. That makes the chip a protocol bridge,
  with the I2C firmware calling the UART firmware as a subroutine. Thread 1 runs a **timing monitor** at the same
  time: it watches the SCL pad and sets `uo[5]` (SCL_VIOL) for good if the clock ever has a low phase shorter than
  about 4.5 us or a high phase shorter than about 3.9 us, whoever caused it (a slave pulling the clock down early,
  say). It costs the master nothing.
- **`uio[6]` and `uio[7]` high: full-duplex UART echo.** Thread 0 receives (`ui[0]` = RX), thread 1 transmits
  (`uo[0]` = TX), and they hand bytes to each other through the channel. Bytes can arrive back to back and each one is
  being echoed while the next is still being received, with both bit clocks exact.

Same silicon, four protocols, chosen by firmware. The original fixed-logic UART
(`reference/uart_tx_fixed.v`) is kept as a reference design.

## Loading your own firmware

The ROM firmware above is only the default. The chip also has a 256-word program memory that the host
fills over the pins, so a new protocol is a new program, not a new chip. Raise `uio[5]` (LOAD), put each
byte on `ui[7:0]` and pulse `uio[4]` (STROBE), low byte of each 16-bit word first, 512 bytes in all, then
lower LOAD and the CPU starts the new program at address 0. A reset without LOAD brings back the ROM
firmware. Details and timing are in `docs/loading.md`; `tools/load_image.py` builds the image from
assembly source. Ready-made programs for I2C and SPI targets, 1-Wire, JTAG, SWD, a CAN receiver, a low-speed USB receiver, WS2812,
PS/2 and MIDI are listed in `docs/examples.md`.

## How to test

Set the mode pins (`uio[7]` for SPI, `uio[6]` for I2C, both for the echo, neither for UART) **before reset**, then in any mode:

1. Put a byte on `ui[7:0]`.
2. Raise `uio[0]` (START) and hold it. The firmware runs one transfer, then waits for START to go low.

UART: watch `uo[0]` (TX); `uo[1]` is BUSY.

SPI: `uo[0]` = CS_N, `uo[1]` = SCK, `uo[2]` = MOSI, `uo[3]` = BUSY, and `uio[1]` = MISO.

I2C: `uio[2]` = SCL and `uio[3]` = SDA (both open-drain, need external pull-ups), `uo[3]` = BUSY, `uo[4]` = ERR (the slave
did not acknowledge), and the byte read is printed on `uo[0]` as UART. `uo[5]` = SCL_VIOL (the monitor thread saw an SCL phase that was too short).

Echo: send UART frames (8N1, 115200 baud) to `ui[0]` (keep it high when idle); they come back on `uo[0]`. No START pin.

Simulation tests live in `test/` and run with `make` using cocotb and Icarus Verilog. They include a
cycle-exact UART bit-timing check, an SPI test against a simulated slave, and I2C tests (read, NACK, clock
stretching) against a simulated EEPROM that also checks the master against the I2C standard-mode timing limits,
plus tests for the echo (back to back and with a 0.4 % fast sender) and for the SCL monitor (a threshold sweep,
legal traffic, and a rogue slave). A random-program differential test runs thousands of random programs, `SPAWN` and
the channel included, on the RTL and on a separate model of the instruction set, comparing every register of every thread after
every clock.

## External hardware

A USB-to-serial adapter or logic analyzer on the output pins; any SPI slave for SPI mode; an I2C EEPROM (e.g. 24Cxx at address 0x50) with pull-ups on SCL and SDA for I2C mode.
